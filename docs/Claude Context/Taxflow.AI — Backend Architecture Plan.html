Backend Architecture Plan · v1.0

Taxflow.AI — production-grade backend architecture

How the system is built underneath: services, data flow, the extraction pipeline, database design, security, hosting and how it scales from 10 firms to 10,000.

Owner: Engineering20 September 2026Companion to the Product PRD

1. Overview

What this document is, and the one decision that shapes everything else.

Purpose

The Product PRD says what Taxflow does. This document says how it's built: which services exist, how a document moves from a WhatsApp photo to an approved, exportable record, how data is stored and secured, and how the system stays up and scales.

The one big decision

Start as a modular monolith, not microservices. A small team building an unproven product should optimise for speed of iteration and low operational overhead, not for a distributed-systems problem it doesn't have yet. The codebase is still organised into clear, decoupled modules (section 4) so it can be split into real services later without a rewrite — but there's only one thing to deploy, monitor and debug on day one.

2. Architecture principles

Six rules that every design decision in this document answers to.

1. Separate what's uncertain from what's exact

AI extraction is probabilistic; tax arithmetic is not. They run as different services with different trust levels, so a bug or a bad model output in one can never silently corrupt the other (see section 6).

2. Everything slow is a background job

Reading a document, sending a WhatsApp message, generating a file — none of these block the user's click. The API responds immediately and the work happens in a queue, with the UI updating when it's done.

3. Every write is attributable

Every row that a person or the system changes is stamped with who/what/when, feeding a single, append-only audit log. This isn't bolted on later — it's a property of the data layer itself (section 8).

4. Multi-tenant by default, isolated by design

One system serves every firm, but a firm can never see another firm's data, even through a bug. This is enforced at the database layer, not just in application code (section 11).

5. Buy commodity infrastructure, build the workflow

Object storage, message queues, OCR baselines and hosting are bought from established providers. The country rules engine, review queue, and deadline logic are what we build and defend.

6. Design for the country pack, not one country

Filing rules, document field requirements and message templates are data (config), never hard-coded logic — because the same backend has to serve every market in the product roadmap without a rewrite.

3. System at a glance

The whole system in one flow: a document's journey from a client's phone to an approved, exportable record.

Client's WhatsApp→ WhatsApp Cloud API→ Webhook receiver→ Message queue→ Ingestion worker
Ingestion worker→ Object storage (Raw)→ Extraction queue→ Extraction worker (OCR + AI)→ Database (draft fields)
Database (draft fields)→ Review queue API→ Accountant approves→ Database (confirmed)→ Rules engine → worksheet / export

Three things to notice: the client never talks to our servers directly (WhatsApp is the intermediary), nothing in the middle row is synchronous with a user waiting on it, and the review step is a hard gate between "the AI's guess" and "data the rest of the system trusts."

5. Document ingestion pipeline, step by step

The most important pipeline in the product — walked through in full detail.

#StepDetail
1Webhook receivedWhatsApp sends a webhook event to our public endpoint when a client sends a message or media. Verified using the provider's signing secret before anything else happens.
2Enqueue, don't processThe webhook handler's only job is to validate the signature and push the raw event onto a queue, then return 200 OK immediately. WhatsApp retries webhooks that don't respond fast, so this step must never do slow work.
3Download mediaA worker pulls the event off the queue, calls the WhatsApp media API to download the actual file (media URLs expire quickly), and computes a content hash.
4DeduplicateIf a file with the same hash already exists for this client this month, it's linked to the existing record instead of creating a duplicate — clients often resend the same photo.
5ValidateFile type and size checks. Corrupted or unsupported files are flagged in an "unsorted" list for a human to handle rather than silently dropped.
6Write to vaultThe Vault Service stores the file in the client's Raw folder for the current year/month, encrypted at rest (section 12).
7Create Document recordA row is created in the database with status received, linked to the client, the source message, and the vault path.
8Enqueue for extractionA message is placed on the extraction queue. Status moves to queued.
9Checklist updateIf the document matches an outstanding checklist item (by type inference), that item is marked as received — pending confirmation once extraction completes.
⚠️Why queues everywhere: WhatsApp can deliver a burst of 50 documents in a minute when a client finally sends everything at once. A synchronous "process on request" design falls over exactly when it matters most. Queues absorb the burst and let workers catch up at their own pace.

6. Extraction & AI layer

How a photo becomes structured, trustworthy data — and where the trust boundary actually sits.

Pipeline

#StepDetail
1Pre-processImage orientation correction, contrast normalisation, PDF-to-image conversion where needed. Cheap, deterministic, runs on every document.
2Classify document typeA lightweight classifier (or rules on filename/context) determines invoice vs. receipt vs. bank statement, since each has a different field schema.
3Extract fieldsA document-understanding model (OCR combined with a vision-capable LLM) reads the fields defined by the active country pack: date, document number, party name, tax ID, line items, tax rate, totals.
4Confidence scoringEvery field gets a 0–1 confidence score, derived from model output probabilities and cross-checks (see step 5). This is stored alongside the value, never discarded.
5Deterministic validationRule-based checks run against the extracted values: does tax = rate × taxable value, does the tax ID match the expected format, do line items sum to the total. A failed check forces a lower confidence score regardless of what the model reported.
6Duplicate & anomaly checksSame invoice number from the same supplier this period? Amount wildly outside this client's normal range? These flags ride alongside the extraction, visible in the review queue.
7Write draft, never confirmedResults are written to the Extraction table with status draft. Nothing downstream (worksheets, exports, dashboards) reads draft data — only confirmed data, ever (see section 8).

Model strategy

Model choice

Use a hosted multimodal LLM API (not a self-trained model) for document understanding at launch — training a custom model needs a volume of labelled data a pre-launch product doesn't have yet. Combine it with a dedicated OCR engine for raw text extraction as a cross-check, since relying on one model for everything hides failure modes.

Cost and routing

Route by document complexity: a clean, printed, single-page invoice can go through a cheaper/faster path; a handwritten or multi-page document routes to a stronger (costlier) model. Track cost and accuracy per document type from day one so this routing improves with real data instead of guesswork.

Data residency for AI calls

Sending a client's financial document to an external AI API is a data transfer that some jurisdictions restrict. Where required, use a regional deployment of the model provider, or a provider with an in-region processing option, and document this per country pack.

Continuous improvement

Every human correction in the review queue (section 5 of the PRD) is captured as a labelled example. This becomes the training/evaluation set for improving prompts, routing rules, and eventually a fine-tuned or specialised model — but only after real volume justifies the investment.

🚫Hard rule: the extraction service never writes to any table that worksheets, exports or client-facing summaries read from. There is no code path where an unreviewed AI output reaches a filing. This is enforced by database permissions, not just application logic — see section 8.

7. WhatsApp integration architecture

Provider layer

Integrate through a Business Solution Provider (BSP) on top of the official WhatsApp Cloud API, rather than the raw Meta API directly — a BSP handles number provisioning, template approval workflow, and delivery infrastructure, which is not worth building in-house pre-launch.

Outbound messages

Every outbound message outside a live 24-hour conversation window must use a pre-approved template. The Messaging Service maintains a local cache of approved templates and their variable slots, and rejects any attempt to send free-form text outside the window before it ever reaches the API.

Inbound handling

A single webhook endpoint receives all events: messages, media, delivery receipts, read receipts, template status changes. Each event type routes to its own handler via the queue (section 5).

Consent and opt-out

A per-contact consent record is required before any outbound template is sent. An inbound "STOP"-equivalent message immediately flips consent to false and blocks all future sends until re-confirmed — checked at send-time, not just at schedule-time.

Failure handling

FailureHandling
Template rejected by MetaSurface clearly in the firm's UI with the rejection reason; never silently retry with the same content.
Message delivery failsRetry with exponential backoff up to a limit, then mark as failed and notify the firm — never fail silently.
Media download expiresMedia URLs from Meta expire in minutes. The ingestion worker downloads immediately on webhook receipt (section 5, step 3) specifically to avoid this.
BSP outageQueue outbound messages and retry once the provider recovers; inbound webhooks queue on the provider's side per their SLA, but a secondary polling fallback is a P1 resilience item.

8. Database design

A relational database (PostgreSQL) is the right default: the data is highly relational (clients → documents → extractions → tasks), correctness matters more than raw write throughput, and its maturity around row-level security is exactly what multi-tenancy needs.

Core schema (simplified)

firms            (id, name, plan, country_pack, created_at)
users            (id, firm_id, email, role, mfa_enabled)
clients          (id, firm_id, legal_name, tax_ids jsonb, jurisdiction,
                   filing_obligations jsonb, whatsapp_number, language,
                   consent_status, consent_at)
checklists       (id, client_id, period_start, period_end, items jsonb)
messages         (id, firm_id, client_id, direction, template_id,
                   body, whatsapp_message_id, status, sent_at)
documents        (id, firm_id, client_id, vault_path, source, content_hash,
                   status, received_at)
extractions      (id, document_id, fields jsonb, confidence jsonb,
                   status,            -- draft | confirmed | rejected
                   confirmed_by, confirmed_at, edit_history jsonb)
tasks            (id, client_id, filing_type, steps jsonb, due_date,
                   status, assignee_id)
outputs          (id, client_id, task_id, type, file_path,
                   source_document_ids uuid[], generated_at)
audit_events     (id, firm_id, actor_id, action, entity_type, entity_id,
                   before jsonb, after jsonb, at, ip)
subscriptions    (id, firm_id, plan, status, current_period_end,
                   documents_used, messages_used)

Key design decisions

Documents and Extractions are separate tables

Mirrors the PRD's data model exactly: the original file's record never changes once created, while its extraction can go through multiple draft → confirmed → edited cycles. This makes "show me the original next to every version of the reading" a simple join, not a reconstruction.

Status is a first-class column, not inferred

extractions.status being explicitly draft or confirmed — rather than inferred from, say, "confidence > 0.9" — means the trust boundary from section 6 is enforced by a WHERE status = 'confirmed' clause that every downstream query uses. It's impossible to accidentally read unreviewed data.

firm_id on every tenant-scoped table

Every table that holds firm-specific data carries a firm_id column, enforced at the database level with row-level security policies (section 11) — not just filtered in application code, where a single missing WHERE clause could leak data across firms.

outputs.source_document_ids

Every generated worksheet or export file stores the exact array of documents it was built from. This is what makes "click any number to see its source invoices" (a core trust principle from the PRD) a database fact, not a UI trick.

audit_events is append-only

No update or delete permission is granted on this table to the application role, only insert and select. Even a compromised application server can't rewrite history.

JSONB for variable, jurisdiction-specific shapes

tax_ids, filing_obligations, fields and confidence vary by country pack and document type. JSONB keeps the schema stable across markets while still being indexable and queryable in PostgreSQL.

Indexing strategy

  • Every foreign key (firm_id, client_id, document_id) is indexed — these are the join paths for nearly every query.
  • A composite index on (client_id, period_start, period_end) on checklists and tasks, since "this client's current period" is the single most common lookup in the product.
  • A GIN index on the JSONB columns that get searched (e.g. searching extracted party names or amounts, per the vault search feature).
  • A partial index on documents where status = 'queued', since the extraction worker polls this exact condition constantly.

9. Document storage (the vault)

Structure

Object storage (S3-compatible), with keys structured as firm_id/client_id/year/month/bucket/filename, mirroring exactly what the PRD's folder-tree UI displays. The UI never invents this structure — it reads it directly from the storage keys.

Encryption

Server-side encryption at rest, with a separate encryption key per firm (envelope encryption via a key management service) so that a key compromise for one firm never exposes another firm's files.

Access pattern

The application never returns a direct storage URL to the browser. Files are served through short-lived, signed URLs generated on request, and every access is logged as an audit event.

Retention

A per-firm, per-jurisdiction retention policy (e.g. keep VAT records five years) drives an automated lifecycle rule — moving old files to cheaper cold storage rather than deleting, unless the firm explicitly requests deletion.

10. API design

Style

A REST API over HTTPS, versioned in the URL path (/v1/...). REST is chosen over GraphQL because the client app's data needs are well-defined and stable (a handful of screens), not the kind of flexible, ad-hoc querying GraphQL earns its complexity for.

Conventions

Resource-based URLs, standard HTTP verbs and status codes, cursor-based pagination for lists, idempotency keys required on every write endpoint that can be safely retried (critical for "send reminder" and "generate worksheet" actions).

Representative endpoints

EndpointPurpose
POST /v1/clientsCreate a client record (or bulk import).
GET /v1/clients/{id}/checklistCurrent period's outstanding items and progress.
POST /v1/clients/{id}/requestsQueue a WhatsApp document request (goes through approval before send).
GET /v1/documents?status=reviewThe review queue, filterable by client, status, confidence.
PATCH /v1/documents/{id}/extractionEdit a field; re-validates and clears the low-confidence flag.
POST /v1/documents/{id}/approveFlips extraction status from draft to confirmed. The single most important write in the system.
POST /v1/tasks/{id}/generate-outputRuns the rules engine against confirmed documents; returns a worksheet or export file, async via job status polling.
GET /v1/dashboardAggregated firm-wide view: at-risk clients, review queue size, recent activity.
POST /webhooks/whatsappInbound provider webhook (signature-verified, not part of the public API surface).

Async job pattern

Any request that triggers slow work (extraction, worksheet generation, bulk messaging) returns 202 Accepted with a job ID immediately. The client polls GET /v1/jobs/{id} or receives a push update — the API never makes a user's browser wait on an AI call.

11. Authentication, authorization & multi-tenancy

Authentication

Email + password with mandatory two-factor authentication for all firm users (accountants handle financial data; this isn't optional). Session tokens are short-lived JWTs with a refresh-token rotation pattern, stored in an HTTP-only cookie.

Authorization (roles)

Four roles per the PRD — owner, senior, junior, read-only — enforced at the API layer via middleware that checks the requesting user's role against the action, before any handler code runs.

Multi-tenancy enforcement

Every authenticated request carries the user's firm_id from their verified session — never from a client-supplied parameter. The database connection for that request sets a session variable consumed by PostgreSQL row-level security policies, so even a query with a bug can't return another firm's rows.

Client-facing surfaces

The WhatsApp channel and the optional client portal never use firm-user authentication. WhatsApp identity comes from the verified phone number; the portal uses single-use, expiring magic links — neither surface can access the firm's internal dashboard.

-- Simplified row-level security example (PostgreSQL)
ALTER TABLE clients ENABLE ROW LEVEL SECURITY;
CREATE POLICY firm_isolation ON clients
  USING (firm_id = current_setting('app.current_firm_id')::uuid);

12. Security architecture

Encryption

TLS 1.2+ everywhere in transit. AES-256 at rest for the database and object storage, with per-firm keys for the vault (section 9) managed through a cloud key management service, not hand-rolled.

Secrets management

API keys, database credentials and provider tokens live in a dedicated secrets manager, never in code, environment files checked into version control, or logs.

Least privilege

Each service module's database role has only the permissions it needs — the extraction worker can insert into extractions but has no delete permission anywhere, and no service role can write to audit_events except through the Audit Service's own insert path.

Input validation

Every API input is validated against a strict schema before touching business logic. File uploads are checked for type and size, and scanned for malware before being written to the vault.

Dependency & vulnerability management

Automated dependency scanning in CI, with a policy of patching critical vulnerabilities within days, not sprints.

Independent testing

A third-party penetration test before the first paid launch, and at least annually after, plus a private vulnerability disclosure channel from day one.

⚠️Certification path: begin SOC 2 Type II (or ISO 27001) readiness work from month one, even though certification itself takes 6–12 months — enterprise firms and some jurisdictions' data-protection expectations will eventually require it, and retrofitting controls is far more expensive than building them in from the start.

13. Infrastructure and deployment

Hosting

A major cloud provider with data centre regions matching the launch market's residency requirements (see the PRD's country packs). Containers (Docker) for every service, orchestrated with a managed container platform rather than self-run Kubernetes — the operational overhead of self-managed Kubernetes isn't justified at this stage.

Infrastructure as code

All infrastructure defined in code (e.g. Terraform), never created by hand in a cloud console. This makes standing up a new region for a new country pack a repeatable, reviewable process instead of tribal knowledge.

Environments

Three environments — development, staging, production — with staging as a full mirror of production topology (using anonymised or synthetic data) so infrastructure and migration changes are tested before they touch real firm data.

CI/CD

Every merge to the main branch runs the automated test suite, then deploys to staging automatically. Production deploys are a deliberate, one-click promotion from a tested staging build — never a direct push to production.

Deployment topology

Load balancer→ API containers (autoscaled)→ PostgreSQL (primary + replica)
Message queue (managed)→ Worker containers (autoscaled)→ Object storage

14. Scaling and performance

BottleneckApproach
Extraction worker throughput during a burst (e.g. filing deadline week)Workers autoscale on queue depth, not CPU — the queue length is the real signal that more capacity is needed.
Database read load from dashboards and review queuesA read replica serves reporting/dashboard queries, keeping the primary free for writes (extraction confirmations, message sends).
Hot tenants (a large firm with thousands of clients)Pagination and query limits enforced at the API layer regardless of plan size; heavy background jobs (bulk reminders) are rate-limited per firm so one tenant can't starve others.
AI extraction cost at scaleModel routing by document complexity (section 6) and caching repeated-supplier templates (the same recurring supplier's invoice layout doesn't need full re-analysis every time).
WhatsApp rate limitsOutbound sends are queued and paced to stay within the provider's per-number throughput limits; a firm's bulk "remind everyone" action spreads over minutes, not one instant burst.

The guiding rule: scale the stateless layers (API, workers) horizontally first — they're cheap and simple to add — and only reach for database sharding or a services split once a specific, measured bottleneck justifies the added complexity.

15. Observability

Logging

Structured (JSON) logs from every service, correlated by a request/trace ID that follows a document from webhook receipt through extraction to approval — so a single support ticket can be traced end to end.

Metrics

Queue depth, extraction latency and accuracy by document type, WhatsApp delivery rate, API error rate and latency by endpoint, database connection pool saturation.

Tracing

Distributed tracing across the async pipeline (webhook → queue → worker → database), essential for diagnosing "why is this document stuck in review" issues in production.

Alerting

Paged alerts for: extraction queue depth growing unbounded, WhatsApp webhook failures, elevated API error rates, and any database replication lag — these directly threaten the product's core promises.

Business dashboards

A separate, non-paging dashboard tracking the PRD's own success metrics (documents processed, review time, fulfilment rate) so product and engineering watch the same numbers.

Error tracking

Automatic capture and grouping of unhandled exceptions across all services, with the same trace ID linking an error back to the specific document or request that caused it.

16. Reliability and disaster recovery

ConcernApproach
Database backupsAutomated daily full backups plus continuous point-in-time recovery, tested with an actual restore drill on a schedule, not just assumed to work.
Object storage durabilityRely on the cloud provider's built-in multi-region redundancy for the vault; cross-region replication for the highest tier of business continuity if a firm's contract requires it.
Queue message lossUse a managed queue with at-least-once delivery and a dead-letter queue for messages that repeatedly fail processing, so a bad document never silently vanishes.
Service outageHealth checks with automatic container restart; the load balancer routes only to healthy instances.
Recovery targetsA concrete RPO (recovery point objective) and RTO (recovery time objective) — for example, RPO of 5 minutes and RTO of 1 hour — set explicitly and tested, not left implicit.
Incident responseA written runbook and an on-call rotation from the first paying customer onward; every incident gets a blameless post-mortem.
